  WORKDIR /web
  COPY frontend/package.json frontend/package-lock.json ./

  COPY frontend/ ./
  RUN npm run build

  COPY backend/app ./app
  COPY --from=web /web/dist /app/frontend/dist

  - `FROM python:3.12-slim` → Python 서버 실행 환경 구성
  - `COPY --from=web` → 앞에서 빌드한 화면 파일만 가져옴

  import json

  ```text

  ```

  - `urllib.request.urlopen(url)` → 지정된 주소로 HTTP 요청을 보내고 응답을 받음
  - `with` → 응답을 사용한 후 자동으로 닫을 수 있도록 관리
  - `r.status` → HTTP 응답 상태 코드 확인
  - `r.read()` → 서버가 보낸 응답 데이터 읽기
  - `json.loads()` → JSON 형식의 데이터를 파이썬 딕셔너리로 변환
  - `200`은 HTTP 요청이 정상 처리되었다는 의미
  - `{'status': 'ok'}`는 서버가 정상 상태라고 응답한 결과

- 파이썬의 **socket 모듈**을 이용해 서버의 특정 포트에 연결할 수 있는지도 확인하는 방법을 배움

  ```python
  import socket

  def is_open(host, port):
      with socket.socket() as s:
          s.settimeout(3)
          return s.connect_ex((host, port)) == 0

  host = "54-180-180-225.sslip.io"

  print({
      port: is_open(host, port)
      for port in (443, 5432, 8000)
  })
  ```

  보고서에 기록된 실행 결과:

  ```text
  {443: True, 5432: False, 8000: False}
  ```

  - `socket.socket()` → 네트워크 연결에 사용할 소켓 생성
  - `settimeout(3)` → 연결이 오래 걸리지 않도록 대기 시간을 3초로 설정
  - `connect_ex()` → 지정된 서버와 포트로 연결 시도
  - 반환값이 `0`이면 연결에 성공했다는 의미
  - 딕셔너리 컴프리헨션을 이용해 포트별 연결 가능 여부를 한 번에 정리
  - `443: True` → HTTPS 포트에 연결 가능
  - `5432: False` → 외부에서 DB 포트에 연결할 수 없음
  - `8000: False` → 외부에서 앱 포트에 직접 연결할 수 없음

## 3. 해결책 또는 시도한 것

- Docker와 AWS EC2의 차이는 각각 담당하는 역할을 기준으로 정리함
  - **Docker:** 프로그램이 실행될 환경을 묶어 주는 기술
  - **AWS EC2:** 프로그램이 실제로 실행될 서버 컴퓨터를 제공하는 서비스
  - Docker가 프로그램을 이사할 수 있도록 포장하는 상자라면 EC2는 그 상자를 가져다 놓을 건물이라는 비유로 이해함
  - 따라서 Docker로 만든 서비스를 EC2에서 실행하면 개발 환경과 운영 환경의 차이를 줄일 수 있다는 것을 알게 됨

- 도메인과 포트의 관계는 도서관 주소와 출입문에 비유해 정리함
  - 도메인은 도서관의 주소
  - IP는 실제 서버를 식별하는 주소
  - 포트는 해당 건물에서 어떤 서비스로 들어갈지 결정하는 문 번호
  - HTTPS는 이용자와 서버 사이에서 주고받는 정보를 암호화하는 방법
  - Caddy는 외부 요청을 받아 적절한 내부 서비스로 전달하는 역할이라고 이해함

- 운영 서버에서 특정 포트를 닫아 두는 이유는 외부 접근과 내부 통신을 구분해 이해함
  - 사용자는 443번 포트를 통해 Caddy에 접속
  - Caddy는 내부 네트워크를 이용해 애플리케이션에 요청 전달
  - 애플리케이션은 내부 네트워크를 통해 DB에 접속
  - 따라서 DB와 앱의 포트를 인터넷에 공개하지 않더라도 내부에서는 정상적으로 통신할 수 있음
  - 불필요한 외부 접근 경로를 줄이는 것이 보안에 중요하다는 점을 알게 됨

- 파이썬의 서버 상태 확인 코드와 포트 확인 코드를 비교하며 각각의 목적을 정리함
  - `urllib.request`는 HTTP 요청을 보내 서버가 정상적으로 응답하는지 확인
  - `socket`은 지정된 서버의 특정 포트에 네트워크 연결이 가능한지 확인
  - HTTP 상태 코드 200이 나왔다고 해서 질문과 답변 등 모든 기능이 정상이라는 의미는 아님
  - 반대로 포트 연결이 가능하더라도 해당 서비스의 실제 기능에는 오류가 있을 수 있음
  - 따라서 서버 상태, 네트워크 연결, 실제 기능을 구분해서 검사해야 한다는 것을 이해함

- 서버에 접속했을 때 질문 기능이 실패한 원인은 보고서의 오류 기록을 통해 확인함
  - 처음에는 서버나 Docker 설정 문제일 수 있다고 생각했지만 로그를 확인한 결과 AI 서비스 크레딧 부족이 원인이었음
  - 질문을 분류하기 위해 AI를 처음 호출하는 단계에서 요청이 거절됨
  - OpenAI 임베딩 서비스는 정상적으로 동작했지만 Anthropic 호출에는 문제가 있었음
  - 또한 답변을 받지 못했는데도 질문 한도가 차감되는 문제가 발견됨
  - 이를 통해 단순히 오류 메시지를 표시하는 것뿐 아니라 오류 원인에 따라 적절하게 처리하는 기능도 필요하다는 점을 알게 됨

- RAG 검색에서 정답을 놓친 원인은 검색 방식의 차이로 정리함
  - 의미 검색은 문장의 의미를 비교하므로 자연스러운 질문에 대응하기 좋지만 전문 용어나 특정 표기를 놓칠 수 있음
  - 단어 검색은 특정 단어를 정확하게 찾는 데 유용하지만 한글과 영어처럼 표기가 달라지면 검색이 어려울 수 있음
  - 두 검색 방식을 함께 활용하는 하이브리드 검색이 이러한 단점을 보완할 수 있을 것으로 이해함
  - 또한 검색 결과에 중복된 자료 조각이 많으면 다른 자료가 상위 결과에서 밀려날 수 있다는 것도 알게 됨

## 4. 느낀점

- 6주차에는 RAG와 MCP를 공부하면서 AI가 자료를 검색하고 답변을 만드는 과정을 이해했는데, 이번 주에는 그렇게 만든 프로그램을 실제로 다른 사람이 사용할 수 있도록 배포하는 과정을 배워서 프로젝트의 전체적인 구조가 조금 더 이해되었음
- 이전에는 코드를 작성하고 내 컴퓨터에서 정상적으로 실행되면 프로그램이 완성되었다고 생각했는데, 실제 서비스로 제공하려면 서버 구성과 보안, 네트워크 설정까지 고려해야 한다는 점을 알게 됨
- 특히 외부에서 접속할 수 있는 포트를 제한하는 과정이 인상 깊었음. 프로그램이 정상적으로 동작하는 것뿐 아니라 불필요한 접근을 막는 것도 개발 과정에서 중요한 부분이라고 느낌
- 파이썬으로 서버 상태와 포트를 확인하는 코드에서 지금까지 배운 함수, `with`, 딕셔너리 컴프리헨션이 사용되는 것을 보니 기초 문법이 실제 서버 관리에도 활용된다는 점이 신기했음
- 서버 접속과 로그인은 정상적으로 동작했지만 AI 서비스 크레딧 문제 때문에 질문 기능이 실패했다는 점도 인상 깊었음. 개발 환경에서 테스트를 통과했더라도 실제 배포 환경에서는 외부 서비스나 설정 때문에 문제가 발생할 수 있다는 것을 알게 됨
- RAG 검색 결과를 분석하면서 의미 검색이 항상 단어 검색보다 정확한 것은 아니라는 점도 새롭게 배웠음. 기술을 선택할 때는 어떤 방식이 더 발전되었는지만 볼 것이 아니라 실제 서비스의 데이터와 질문에 적합한지도 확인해야겠다고 느낌
- 다음 주에는 배포된 서비스의 문제를 해결한 뒤 실제 질문과 답변이 정상적으로 동작하는지 확인하고, 프로젝트의 전체 기능을 소개하는 데모 영상과 README를 정리하는 과정도 살펴보고 싶음.
