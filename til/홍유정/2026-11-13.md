  - `__name`처럼 밑줄 두 개를 붙이면 이름 맹글링(name mangling)이 적용되지만, 이것도 완전한 접근 차단은 아님

## 2. 어려웠던 것

- 데코레이터를 처음 배웠을 때 `@` 기호 하나로 함수에 기능을 추가할 수 있다는 것이 잘 이해되지 않았음
  - 특히 `@dataclass`와 `@app.get("/health")`가 같은 형태로 작성되어 있지만 서로 다른 일을 한다는 점이 헷갈렸음
  - 기존 함수나 클래스의 어느 부분이 달라지는 것인지도 처음에는 쉽게 떠오르지 않았음
- 캡슐화도 처음에는 변수 앞에 `_`를 붙이면 외부에서 접근할 수 없게 되는 것이라고 생각했는데, 실제로는 개발자가 내부 사용을 표시하는 관례라는 점을 구분해야 했음
- 이전 대화의 맥락을 참고하여 답변하는 기능도 단순히 대화 기록을 저장하는 것과 어떤 차이가 있는지 이해하기 어려웠음
  - 이전 질문을 참고해 검색에 적합한 문장을 다시 만들고, 그 문장으로 관련 자료를 찾아야 한다는 과정을 새롭게 알게 됨
- 마지막으로 정확도가 91.7%에서 94.4%로 올라간 결과를 보고 처음에는 확실한 성능 개선이라고 생각했지만, 실제로는 한 문항 차이라는 점을 고려해야 해서 수치를 해석하는 것도 쉽지 않았음

## 3. 해결책 또는 시도한 것

- 데코레이터의 개념을 이해하기 위해 이전 주차에 배웠던 코드와 연결해서 정리함
  - `@dataclass`는 클래스에서 반복적으로 작성해야 하는 코드를 줄여 주는 역할
  - `@app.get("/health")`는 특정 주소로 요청이 들어왔을 때 어떤 함수를 실행할지 연결하는 역할
  - 둘 다 데코레이터 문법이지만 실제로 수행하는 일은 다를 수 있다는 점을 구분함
  - 7주차에 서버 상태 코드 `200`을 확인했던 경험과 연결하니 `@app.get("/health")`의 목적을 이해하기 쉬웠음

- 캡슐화는 4주차 객체지향 실습과 비교하면서 복습함
  - 클래스는 관련된 데이터와 기능을 하나로 관리하기 위한 구조임
  - 상속은 기존 클래스의 기능을 재사용하거나 확장하기 위한 방법임
  - 캡슐화는 클래스 안의 데이터를 정해진 방식으로 다루도록 설계하는 것임
  - 각각의 개념이 서로 다른 목적을 가지고 있지만 실제 프로그램에서는 함께 사용될 수 있다는 것을 정리함

- 이어지는 대화 기능은 기존 검색 과정과 비교하며 이해하려고 함
  - 기존 방식: 사용자 질문 → 질문 분석 → 자료 검색 → 답변 생성
  - 개선 방식: 사용자 질문 → 이전 대화 참고 → 검색에 적합한 질문으로 재구성 → 자료 검색 → 답변 생성
  - RAG는 답변에 필요한 자료를 먼저 검색하는 방식이고, 이번 개선은 그 검색에 사용할 질문을 더 구체적으로 만드는 과정이라는 점을 알게 됨
  - 또한 사용자 권한은 AI가 판단하는 것이 아니라 프로그램이 검사한다는 기존 원칙이 그대로 유지된다는 점을 확인함

- 1주차부터 8주차까지의 학습 내용을 되짚어 보며 배운 개념을 서로 연결함
  - Python 기초 문법 → 함수와 모듈 → 클래스와 상속 → 예외처리와 컴프리헨션 → 캡슐화와 데코레이터
  - RAG → MCP 검색 도구 → 질문 분류 → Agent Loop → 출처 확인
  - Docker → AWS EC2 → Caddy → 외부 접속과 보안
  - 각각 별도로 배울 때는 어려웠지만, 실제 서비스에서 어떤 역할을 하는지 연결하니 전체 구조를 이해하는 데 도움이 되었음
