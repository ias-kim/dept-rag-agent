# 2026-10-30 TIL

## 1. 오늘 배운 것

- 5주차까지는 질문을 받으면 안내 데스크(라우터)가 정해진 규칙에 따라 검색 도구를 골랐는데, 6주차에는 AI가 직접 필요한 도구를 선택하고 자료가 부족하면 다시 검색하는 **Agent Loop** 방식이 추가되었다는 것을 배움
  - 기존 방식은 질문을 `academic` / `major` / `both` / `none`으로 분류한 뒤 프로그램이 도구를 선택
  - Agent Loop는 AI가 사용할 수 있는 도구 목록을 확인한 후 직접 도구와 검색어를 결정
  - AI가 자유롭게 도구를 선택하더라도 사용자의 권한을 넘어서 자료에 접근하지 못하도록 프로그램에서 제한
  - 이번 주에는 이러한 서비스의 동작을 이해하기 위해 RAG와 MCP의 기본 개념을 학습함

- **RAG(Retrieval-Augmented Generation)**는 AI가 자신의 기억에만 의존하지 않고 외부 자료에서 관련 내용을 검색한 후 답변하는 방식이라는 것을 배움
  - 일반적인 AI는 우리 학과의 시간표나 강의자료처럼 학습하지 않은 정보를 정확하게 알기 어려움
  - 이런 질문에 추측으로 답하면 실제 자료와 다른 내용을 만들어 낼 수 있음
  - RAG는 질문과 관련된 자료를 먼저 찾고, 검색된 내용을 AI에게 전달해 답변하도록 함
  - 도서관에 비유하면 사서가 기억만으로 답하는 것이 아니라 책을 찾아 해당 페이지를 확인한 후 설명하는 것과 같음

- 우리 프로젝트에서 RAG가 작동하는 과정은 크게 세 단계로 나뉜다는 것을 배움
  1. **자료 분할 및 색인:** PDF 강의자료를 작은 조각으로 나누고 파일명·페이지 등의 정보를 저장
  2. **관련 자료 검색:** 사용자의 질문과 관련된 자료 조각을 검색
  3. **답변 생성 및 출처 표시:** 검색한 내용을 바탕으로 답변하고 근거 자료의 파일명과 페이지를 함께 표시

- RAG의 검색 원리를 이해하기 위해 파이썬 리스트와 딕셔너리를 이용한 간단한 자료 검색 코드를 학습함

  ```python
  cards = [
      {"쪽": 20, "내용": "2학년 일본어 특강 월~목 8~9교시"},
      {"쪽": 2, "내용": "일본어 특강 장소 304호"},
      {"쪽": 5, "내용": "추석 연휴 강의실 폐쇄"},
  ]

  question = "일본어 특강"

  found = [c for c in cards if question in c["내용"]]

  print([c["쪽"] for c in found])
  ```

  실행 결과:

  ```text
  [20, 2]
  ```

  - `cards`는 자료의 페이지와 내용을 딕셔너리로 저장한 리스트
  - `question`은 사용자가 입력한 검색어
  - `if question in c["내용"]`은 자료 내용에 검색어가 포함되어 있는지 확인
  - 리스트 컴프리헨션을 이용해 조건에 맞는 자료만 `found`에 저장
  - 마지막에는 검색 결과의 페이지 번호만 추출해 출력
  - 검색어를 `"추석"`으로 바꾸면 5쪽 자료만 검색된다는 것도 확인할 수 있음

- 실제 RAG 서비스에서는 단순히 같은 글자가 포함되어 있는지만 확인하지 않고 **임베딩(Embedding)**을 이용해 의미가 비슷한 자료를 검색한다는 것을 배움
  - 문장의 의미를 숫자로 표현하고 질문과 자료 사이의 유사도를 비교
  - 질문과 자료에 완전히 같은 단어가 없어도 의미가 비슷하면 검색할 수 있음
  - 다만 자료 자체에 정답이 없다면 검색 방법만 개선한다고 해결되는 것은 아님
  - 실제로 기존 예시 질문 중 ACID 성질과 중간고사 기간은 자료에 해당 내용이 없어 답변할 수 없었던 것이므로, 자료가 존재하는 질문으로 변경되었다는 것을 알게 됨

- **MCP(Model Context Protocol)**는 AI와 외부 도구를 일정한 규격으로 연결하기 위한 표준이라는 것을 배움
  - AI가 학사 검색, 전공 검색 등 여러 도구를 사용할 때 각각 연결 방식이 다르면 도구가 추가될 때마다 연결 코드를 수정해야 함
  - MCP는 도구의 이름, 설명, 입력값 등을 공통된 형식으로 제공
  - 도서관에 비유하면 각 검색 창구에 이름과 이용 방법이 적힌 동일한 형식의 안내판을 붙이는 것과 같음
  - AI는 안내판을 확인하고 질문에 적합한 도구를 선택할 수 있음

- MCP 도구의 구조를 이해하기 위해 딕셔너리로 도구 정보를 표현하는 코드를 학습함

  ```python
  tool = {
      "name": "search_academic",
      "description": "학사 공지·시간표에서 찾기",
      "input": {
          "query": "검색어(문자열)"
      }
  }

  print(tool["name"], "-", tool["description"])
  ```

  실행 결과:

  ```text
  search_academic - 학사 공지·시간표에서 찾기
  ```

  - `name`: 도구를 구분하는 이름
  - `description`: 도구가 어떤 작업을 수행하는지 설명
  - `input`: 도구를 호출할 때 필요한 입력값
  - 이처럼 정해진 구조로 정보를 제공하면 AI가 도구의 역할과 사용 방법을 파악할 수 있음
  - 전공 검색 도구 역시 같은 형식으로 표현할 수 있다는 것을 이해함

- 사용자 역할에 따라 MCP 도구 접근 권한이 달라진다는 것을 배움
  - **수강생:** 학사 자료와 본인이 수강하는 과목의 전공 자료 검색 가능
  - **게스트:** 학사 자료 검색 가능, 전공 검색 도구는 목록에 표시되지 않음
  - **평가용 계정:** 모든 과목 자료에 접근 가능
  - 첫 번째 권한 검사에서는 사용자에게 허용된 도구만 목록으로 제공
  - 두 번째 권한 검사에서는 전공 검색 시 실제 수강 과목과 검색 조건을 다시 비교
  - AI가 권한을 스스로 판단하는 것이 아니라 프로그램에서 접근을 제한한다는 점이 중요함

- Agent Loop가 동작하는 네 가지 요소도 함께 학습함
  1. **도구 목록 확인:** `client.list_tools()`로 현재 사용자에게 허용된 도구 목록을 가져옴
  2. **도구 실행:** AI가 선택한 도구와 검색어를 MCP 서버에 전달해 자료를 검색
  3. **검색 결과 누적:** 여러 번 검색한 결과를 모으고 동일한 자료 조각은 중복되지 않도록 처리
  4. **종료 조건 확인:** AI가 답변을 완료하거나 검색 횟수가 최대 4회에 도달하면 검색 종료

- 검색 횟수를 최대 4회로 제한하는 이유도 이해함
  - AI가 계속 자료를 찾으려고 하면 응답 시간이 길어지고 불필요한 도구 호출이 발생할 수 있음
  - 따라서 AI의 판단에만 맡기지 않고 프로그램에서 검색 횟수를 강제로 제한
  - 4회에 도달하면 지금까지 수집한 자료를 이용해 답변을 생성하도록 함
  - 검색 결과를 누적할 때는 `chunk_id`로 중복을 확인하고, 같은 자료가 다시 검색되면 점수가 더 높은 결과를 유지

- 기존 안내 데스크 방식과 Agent Loop 방식의 비교 결과도 확인함

  | 항목 | 안내 데스크 | Agent Loop |
  |---|---|---|
  | 답변 정확도 | 33/36 (91.7%) | 33/36 (91.7%) |
  | 근거 쪽을 찾은 비율 | 90.0% | 83.3% |
  | 응답 시간(중앙값) | 3.1초 | 3.8초 |
  | 질문당 평균 검색 횟수 | - | 1.2회 |
  | 검색 중 오류 | 0건 | 0건 |

  - 두 방식의 답변 정확도는 동일했지만 서로 틀린 문제가 달랐음
  - Agent Loop는 기존 방식이 놓친 SAVEPOINT 관련 질문을 맞혔지만, 데코레이터 관련 질문에서는 한 번 검색한 뒤 추가로 찾지 않아 정답을 놓침
  - 따라서 AI가 직접 도구를 선택한다고 해서 반드시 기존 방식보다 정확한 것은 아니라는 점을 알게 됨

## 2. 어려웠던 것

- 처음에는 RAG가 일반적인 AI 답변과 어떻게 다른지 헷갈렸음. AI도 이미 많은 정보를 알고 있는데 굳이 자료를 먼저 검색해야 하는 이유가 바로 이해되지 않았음
- RAG 실습 코드에서는 단순히 문자열이 포함되어 있는지만 검사하는데, 실제 서비스에서는 의미가 비슷한 자료도 찾는다고 해서 두 방식의 차이가 어려웠음
- MCP는 AI가 사용하는 검색 도구라고 생각했는데, 정확히는 검색 기능 자체가 아니라 도구를 연결하는 표준이라는 점이 헷갈렸음
- Agent Loop에서 AI가 스스로 도구를 선택한다면 게스트가 전공 검색을 요청할 때도 접근할 수 있는 것이 아닌지 의문이 들었음
- 검색을 여러 번 수행한 결과를 누적할 때 같은 자료가 중복되면 어떻게 처리하는지, 최대 검색 횟수를 왜 프로그램에서 제한해야 하는지도 처음에는 이해하기 어려웠음

## 3. 해결책 또는 시도한 것

- RAG와 일반적인 AI 답변의 차이는 도서관 비유를 이용해 정리함
  - 일반적인 답변은 사서가 기억에 의존해 설명하는 방식
  - RAG는 먼저 관련 책을 찾고 실제 내용을 확인한 후 답변하는 방식
  - 우리 프로젝트처럼 학교 내부 자료를 다루는 경우에는 검색 과정이 특히 중요하다는 것을 이해함

- RAG의 자료 검색 과정을 이해하기 위해 파이썬 실습 코드를 단계별로 분석함
  - 자료를 리스트 안의 딕셔너리로 표현
  - `for`문과 `if` 조건으로 질문에 해당하는 자료를 선택
  - 검색어를 `"일본어 특강"`에서 `"추석"`으로 변경해 검색 결과가 달라지는 것을 확인
  - 앞서 배운 리스트 컴프리헨션이 실제 RAG의 자료 검색 원리를 설명하는 데 사용된다는 점을 알게 됨

- 단순 문자열 검색과 임베딩 검색은 검색 기준이 다르다는 점으로 구분해 이해함
  - 문자열 검색은 같은 글자가 포함되어 있는지 확인
  - 임베딩 검색은 문장의 의미가 얼마나 비슷한지 비교
  - 다만 어떤 검색 방식이든 원본 자료에 없는 정보까지 보장할 수는 없으므로, 검색 결과와 출처를 확인하는 과정이 중요하다고 정리함

- MCP는 도구 자체가 아니라 도구를 연결하는 규격이라는 점에 집중해 이해함
  - 학사 검색과 전공 검색은 각각 다른 기능을 수행하는 도구
  - MCP는 이러한 도구들의 이름, 설명, 입력값을 공통된 구조로 제공
  - 파이썬 딕셔너리로 도구 정보를 표현해 보니 이전에 배운 자료구조와 연결되어 이해하기 쉬웠음

- 게스트의 전공 검색 제한은 **AI의 판단과 실제 접근 권한을 분리하는 구조**로 이해함
  - AI가 검색하고 싶어 하더라도 게스트에게는 전공 검색 도구가 처음부터 제공되지 않음
  - 수강생도 다른 과목의 자료를 요청하면 검색 단계에서 허용된 과목만 남기도록 제한
  - 따라서 질문에 "나는 수강생이야"라고 적는 것만으로 실제 접근 권한이 바뀌지 않음
  - 4주차에 배웠던 권한 검사 원칙이 Agent Loop에서도 그대로 유지된다는 것을 알게 됨

- Agent Loop의 검색 결과 누적 과정은 딕셔너리의 키를 이용한 중복 검사와 연결해 이해함
  - `chunk_id`를 키로 사용해 이미 검색한 자료인지 확인
  - 처음 나온 자료는 저장하고, 중복된 자료는 검색 점수를 비교
  - 마지막 검색 결과만 남기지 않고 이전에 찾은 자료도 보존해야 답변의 출처를 정확히 확인할 수 있음
  - 최대 4회 제한 역시 반복문의 종료 조건을 프로그램이 관리한다는 관점에서 이해함

## 4. 느낀점

- 5주차에는 학생이 브라우저에서 질문하고 답변의 출처를 확인하는 화면을 배웠는데, 이번 주에는 그 답변이 어떤 과정을 거쳐 만들어지는지 RAG를 통해 이해할 수 있어서 좋았음
- 이전에 배운 리스트, 딕셔너리, 컴프리헨션이 실제 프로젝트의 자료 검색과 도구 정보 관리에 활용된다는 점이 인상 깊었음. 처음 배울 때는 단순한 문법이라고 생각했는데 실제 서비스의 구조와 연결해 보니 왜 필요한지 조금 더 이해하게 됨
- MCP는 처음에는 어려운 개념처럼 느껴졌지만, 도서관의 여러 창구를 같은 규격으로 연결한다는 비유를 통해 이해하니 생각보다 단순한 원리라는 것을 알게 됨
- 특히 AI가 스스로 도구를 선택하더라도 사용자의 권한까지 마음대로 결정하는 것은 아니라는 점이 인상 깊었음. AI의 기능이 많아질수록 프로그램에서 권한과 실행 조건을 명확히 관리하는 것이 중요하다고 느낌
- 두 방식의 정확도가 모두 91.7%였지만 서로 다른 문제를 틀렸다는 결과도 흥미로웠음. 새로운 방식을 도입했다고 무조건 성능이 좋아지는 것은 아니므로 실제 테스트 결과를 비교하고 원인을 분석하는 과정이 필요하다는 것을 알게 됨
- 다음 주에는 Docker로 구성한 서비스를 AWS EC2에 배포하는 과정을 살펴보고, 외부에서도 로그인과 질문 및 근거 자료 확인이 정상적으로 이루어지는지 알아보고 싶음.
