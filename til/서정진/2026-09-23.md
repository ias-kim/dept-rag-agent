# 2026-09-23 TIL

## 1. 오늘 배운 것

- AI가 찾아볼 "학과 지식 도서관"을 채우는 자료 적재 과정은 5단계로 나뉜다는 것을 배움
  - 자료 수집: 강의자료·시간표·공지를 한곳에 모아야 AI가 지어내지 않고 실제 자료로만 답할 수 있음
  - 전처리: 매 쪽 반복되는 학교명·교수명·쪽번호를 지워야 검색이 내용과 상관없는 쪽을 찾아오지 않음 (전체 글자의 6.3%가 반복 문구였음)
  - 문서 분할(Chunking): 긴 문서를 "조각 하나만 읽어도 답할 수 있는" 크기로 쪼갬
  - 메타데이터: 조각마다 `source`·`page`·`section`·`scope`·`course` 꼬리표 5종을 붙여야 출처 표시와 권한 필터가 가능함
  - 임베딩: 문장의 뜻을 숫자 1,536개로 바꿔 두면 "수강신청 마감"과 "신청 기한"처럼 표현이 달라도 뜻이 가까운 조각을 찾을 수 있음
- 분할 방식은 감으로 고르지 않고 실제 자료 121개 문서에 두 방식을 모두 적용해 수치로 비교한 뒤 결정함
  - 고정 길이(800자): 제목 보존 7.1%, 문장 중간 끊김 2.2%
  - 구조 기반(슬라이드 1장 = 조각 1개, 채택): 제목 보존 99.0%, 문장 중간 끊김 0.0%
- 1주차에 말로만 들었던 "처리 과정은 한 벌, 저장 공간만 둘"이 실제로는 저장 공간 하나에 `scope` 꼬리표로 전공 색인(3,679조각)과 학사 색인(48조각)을 나누는 모습이라는 것을 확인함
- 권한 관문 두 겹이 실제 코드에서 어디에 있는지 확인함
  - 관문①: MCP 서버가 사용자마다 다른 도구 목록을 내줌 → 수강 과목이 없으면 전공자료 검색 도구가 목록에 아예 없음
  - 관문②: 검색 조회문에 수강 과목 조건을 함께 넣음 → 수강하지 않은 과목의 조각은 검색 결과에 나오지 않음
- MCP는 두 단계로 동작한다는 것을 배움
  - `list_tools`: 서버가 "내가 할 수 있는 일" 목록을 클라이언트에 내줌
  - `call_tool`: 클라이언트(AI)가 그 목록에서 도구를 골라 호출하면 서버가 실행해서 결과를 돌려줌

## 2. 어려웠던 것

- 문서를 조각으로 나눈다는 개념 자체는 금방 이해했는데, 왜 "자르는 단위"에 따라 검색 결과가 달라지는지는 처음에 와닿지 않았음
- 권한 필터 코드에서 `scope == "academic"` 조건과 `scope == "major" and course_code in allowed_courses` 조건이 `or_`로 묶여 있는 구조가 처음엔 헷갈렸음
- 머리글을 지울 때 숫자를 모두 떼고 비교하면 "Chapter 11", "Chapter 12" 같은 슬라이드 제목까지 머리글로 오인되어 지워진다는 문제가 왜 생기는지 바로 이해하지 못했음

## 3. 해결책 또는 시도한 것

- 고정 길이와 구조 기반 두 방식의 결과 수치를 직접 비교해 보니, 고정 길이는 문장이 중간에 끊기고 슬라이드 제목이 대부분 사라져서 조각만 봐서는 무슨 내용인지 알기 어렵다는 게 납득됨
- 권한 필터는 "학사 공지는 누구나 보고, 전공 자료는 수강 과목일 때만 본다"는 두 갈래를 한 문장으로 쓴 것이라고 정리하니 이해됨. 또 `allowed_courses`는 AI가 만든 값이 아니라 서버가 데이터베이스에서 꺼내 넣는 값이라는 점이 중요하다는 걸 알게 됨
- 머리글 문제는 "쪽번호가 아닌 숫자까지 떼어 낸 것"이 원인이었고, 줄 앞뒤 숫자가 그 쪽의 쪽번호와 정확히 같을 때만 떼도록 고친 `_key` 함수 코드를 읽으며 확인함
- 지난주에 미리 읽어 오기로 한 MCP 공식 문서 내용을 우리 서버 코드와 연결해서 `list_tools` → `call_tool` 흐름을 순서대로 따라가 봄

## 4. 느낀점

- 설계할 때는 안 보이던 문제(스캔 PDF, 중복 파일, 머리글 오인)가 실제 자료를 넣는 순간 드러난다는 것을 느낌
- 결정을 내릴 때 "이게 더 좋아 보여서"가 아니라 비교한 수치를 근거로 남기는 습관을 들여야겠다고 생각함
