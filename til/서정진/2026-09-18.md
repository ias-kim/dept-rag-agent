# 2026-09-18 TIL

## 1. 오늘 배운 것

- 기술 스택은 "유명해서"가 아니라 우리 서비스 조건(1·2학년 공동 개발, 한국어 자료, 권한별 검색)에 맞는지로 고른다는 것을 배움
  - Python: 수업에서 배우는 언어라 팀 전원이 같은 코드베이스에 기여할 수 있음
  - FastAPI: 비동기 구조를 기본 제공해서 검색을 기다리는 동안 다른 요청을 처리할 수 있음
  - OpenAI `text-embedding-3-small`: 한국어 자료를 다루면서 비용이 낮음
  - PostgreSQL + pgvector: 접근 권한 필터를 조회문(SQL) 조건 한 줄로 걸 수 있음
  - Docker + AWS EC2: 실행 환경을 한 덩어리로 묶어 어느 서버에서든 똑같이 동작
- MCP(Model Context Protocol)는 검색 같은 기능을 표준 규격으로 AI에게 노출하는 방식이라, 기능이 늘어나도 AI 쪽 코드는 그대로 두고 도구만 추가하면 됨
- 자료 처리 과정(텍스트 추출 → 분할 → 임베딩 → 적재)은 한 벌만 만들고, 저장 공간만 전공용/공지용 둘로 나눔. 자료 종류가 늘어나면 저장 공간만 추가하면 됨
- "하지 않기로 한 것"도 설계 결정이라는 것을 배움
  - LangChain 같은 RAG 프레임워크 대신 구성 요소를 직접 구현 → 어느 단계에서 품질이 떨어지는지 직접 파악하기 위함
  - Redis 같은 비동기 작업 큐는 도입하지 않음 → 검색 응답이 수 초 안에 끝나 대기열이 필요 없음

## 2. 어려웠던 것

- MCP라는 용어가 처음이라 "도구를 노출한다"는 말이 무슨 뜻인지 바로 와닿지 않았음
- 처리 과정을 하나로 만들면서 저장 공간만 둘로 나눈다는 게 구체적으로 어떤 모습인지 그려지지 않았음

## 3. 해결책 또는 시도한 것

- 질문 하나가 들어왔을 때 어떤 순서로 무엇이 호출되는지를 단계로 나눠 직접 그려보고, 각 단계의 판단 주체가 누구인지 말로 설명해 봄
- 저장 공간 분리는 "처리 코드는 하나, 넣는 곳(색인)만 전공용/공지용으로 다른 것"으로 정리하니 이해됨
- 2주차 전에 MCP 공식 문서를 미리 읽어 오기로 함

## 4. 느낀점

- 기술 이름을 외우는 것보다 "왜 이걸 골랐는지"를 설명할 수 있어야 설계를 이해한 것이라고 느낌
- 프레임워크를 안 쓰고 직접 만든다고 하니 2주차 파이프라인 구현이 조금 부담되지만, 단계별로 확인할 수 있다는 점은 좋다고 생각함
