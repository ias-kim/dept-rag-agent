## 1. 오늘 배운 것

- 5주차까지는 안내 데스크(라우터)가 정해진 처리 표대로 도구를 골랐는데, 6주차에는 AI(사서)가 직접 도구를 골라 찾아보고 모자라면 다시 찾는 Agent Loop를 더했다는 것을 배움
  - 학사+전공이 섞인 질문은 두 도구를 한 번에 찾고, 다시 찾기는 4회에서 프로그램이 끊음
  - AI에게 고를 자유를 주는 만큼 "AI가 알아서 조심하겠지"에 기대면 안 되고, 권한을 먼저 정리하고 다시 검증해야 한다는 게 이번 주의 출발점이었음
- 역할은 세 가지로 정리함
  - 수강생(수강 과목 있음) / 게스트(수강 과목 없음) / 평가용 계정(전 과목)
  - 관리자 기능은 화면에 두지 않고 서버 명령(`make users`)으로만 실행
- 1주차부터 지켜 온 권한 두 겹을 Agent Loop 코드에서 다시 찾아봄
  - 첫째 겹(도구 목록): `client.list_tools()`로 받은 목록을 그대로 AI에게 넘김 → 게스트는 전공 검색 도구가 목록에 없어서 AI가 고를 수조차 없음. 목록을 손으로 만들면 이 겹이 무너짐
  - 둘째 겹(검색 조건): 수강생이 다른 과목 코드를 넣어도 검색 조건에서 자기 수강 과목과 겹치는 부분만 남음 (3주차 `allowed = user.courses & {...}`와 같은 자리)
  - 그 아래 원칙: AI에게 보내는 내용에는 역할이나 수강 과목을 넣지 않음 → AI가 무엇을 알든 권한은 프로그램이 정함
- 권한 테스트 행렬로 다시 검증함
  - 답변 방식 3종(바로 찾기·안내 데스크·Agent Loop) × 게스트·수강생 조합마다 남의 전공 조각이 답·출처·AI에게 보낸 내용 어디에도 안 나오는지 확인
  - 권한 검사 한 줄을 일부러 지우고 테스트가 실제로 실패하는 걸 본 뒤 되돌림 → 테스트가 "진짜 막는지" 확인하는 방법
- Agent Loop 4요소를 `backend/app/core/agent.py`에서 한 줄씩 찾아봄

  ```python
  listed = (await client.list_tools()).tools                         # ① 서가 지도 받기
  tools = [to_model_tool(t) for t in listed]
  while True:
      response = llm.beta.messages.create(..., tools=tools, messages=messages)
      uses = [b for b in response.content if b.type == "tool_use"]
      if response.stop_reason != "tool_use" or not uses:              # ④-1 더 안 찾으면 끝
          return finish(_final_answer(response, _sorted_hits(found)))
      messages.append({"role": "assistant", "content": response.content})
      results = []
      for use in uses[:s.agent_max_tool_calls - calls_used]:
          calls_used += 1
          hits = parse_hits(await client.call_tool(use.name, use.input))  # ② 찾기
          for h in hits:                                              # ③ 모으기
              if h.chunk_id not in found or h.score > found[h.chunk_id].score:
                  found[h.chunk_id] = h
          results.append({"type": "tool_result", "tool_use_id": use.id,
                          "content": render_chunks(hits) or NO_RESULTS})
      if calls_used >= s.agent_max_tool_calls:                        # ④-2 4회면 멈춤
          break
      messages.append({"role": "user", "content": results})
  forced = generate_answer(llm, question, _sorted_hits(found), ...)
  ```

  - `uses[:s.agent_max_tool_calls - calls_used]` → AI가 한 번에 여러 곳을 찾겠다고 해도 남은 횟수만큼만 실행함. 상한 4회는 AI가 아니라 프로그램이 지킴
  - `found[h.chunk_id] = h` → 여러 번 찾은 조각을 조각 번호로 모으고, 같은 조각이면 점수 높은 쪽만 남김. 마지막 찾기 결과만 남기면 앞에서 찾은 조각을 인용한 정상 문장이 "출처 없음"이 됨
  - `messages.append(... response.content)` → AI의 이전 응답을 손대지 않고 그대로 돌려줌. 일부를 빼거나 다시 만들면 AI 서비스가 요청을 거절함
  - `generate_answer(...)` → 4회에 이르면 AI에게 더 묻지 않고 모은 조각으로 바로 답을 만듦. 안내 데스크와 같은 답 만들기·출처 검사 코드를 지나서 두 방식을 공정하게 비교할 수 있음
- 잘못된 요청과 오류도 프로그램이 처리한다는 것을 배움
  - 없는 도구 이름이나 500자 넘는 검색어는 실제로 찾지 않고 "잘못된 요청"으로 돌려보냄 → 이것도 4회 안에 셈
  - 찾던 중 오류가 나면 오류 원문 대신 정해진 안내 문장만 AI에게 보냄 → 내부 오류 문장이 학생에게 보이는 답으로 옮겨지지 않게
- 통합 테스트로 로그인 → 질문(`/api/ask`) → 답·근거 자료까지 실제 서버 코드로 한 번에 확인함
  - 수강생은 자기 과목 자료로 답하고 질문 한도는 한 번만 깎임, 게스트는 전공 자료를 받지 못함
  - 검색 서비스가 멈추면 "잠시 후 다시" 안내와 함께 깎인 한도를 되돌림
  - 자동 테스트 서버 346개·화면 44개 모두 통과, 테스트는 가짜 AI 응답으로 돌아서 실제 AI로 5개 질문을 따로 던져 확인함

## 2. 어려웠던 것

- 두 방식의 답변 정확도가 똑같이 91.7%라서 처음엔 "그럼 둘 중 아무거나 써도 되는 것 아닌가" 싶었는데, 근거 쪽을 찾은 비율은 Agent Loop가 더 낮아서 어느 쪽이 나은지 판단이 안 섰음
- 수강 과목 없는 학생이 전공 질문을 하면 안내 데스크는 "수강생만 볼 수 있는 자료"라고 알려 주는데, Agent Loop는 그냥 "자료에서 찾을 수 없다"고만 답해서 왜 이렇게 덜 친절해졌는지 헷갈렸음
- 지난주 보고서에서 "ACID 트랜잭션의 성질"이 안 나오는 원인을 자료 찾기 문제로 적었는데, 이번에 확인해 보니 DB 강의자료에 그 내용이 아예 없었음

## 3. 해결책 또는 시도한 것

- 맞힌 개수가 아니라 틀린 문항을 나란히 놓고 보니, Agent Loop는 더 깊이 찾아서 맞힌 문항도 있고 한 번 찾고 금방 포기해서 놓친 문항도 있었음. 숫자 하나로 비교하지 말고 문항별로 봐야 한다고 정리함 → 7주차 비교표에 함께 정리하기로 함
- 덜 친절한 안내는 "AI에게 역할·수강 과목을 넣지 않는다"는 원칙 때문이라는 걸 코드에서 확인함. AI가 학생 등급을 모르니 "수강생 전용"이라고 말할 수 없는 것. 이 원칙을 지키는 선에서 안내를 보여 줄 방법을 검토하기로 함
- 권한 두 겹이 코드 어디에 있는지(`list_tools` 목록을 그대로 넘기는 줄, 검색 조건의 교집합 줄)를 직접 짚어서 팀원들에게 설명함. 설명하려고 하니 "목록을 손으로 만들면 왜 첫째 겹이 무너지는지"까지 말로 풀어야 해서 더 확실히 이해됨
- 화면 예시 질문은 실제 자료로 답이 나오는지 직접 확인한 것만 두기로 하고, 예시를 일본어 특강·외래키 질문으로 바꿈
